System architecture

Job Search Tracker

Headless searches run once a day per track, verify postings against real career pages, and report what they find to a small API. The tracker page reads and edits the same rows. The machine also runs one nightly task that isn't a search: it reads the postings behind applications logged as nothing but a URL.

How it works

01 · Runs

scripts/setup-scheduler.ps1 registers one Task Scheduler task per track per person, at the track's schedule_time, or staggered 30 minutes apart where none is set. A track with fed_by set gets no task: its sibling's search fills that tab.

Each task runs run-search.ps1. It fetches the prompt from /api/prompt/<track> and the person's documents from /api/documents into <DataDir>\<user-id>\.run\<track>, copies tracker.ps1 in beside them, and runs claude -p there with a fixed tool list. Afterwards it uploads any doc whose contents changed.

The run reaches the API through ./tracker: dedup for what the track already holds and companies for tonight's slice of the company list, then leads, screened, verified, delist, swept and run to report. There is one company list for the whole deployment; each track reads 24 companies a night from it, from its own cursor, and keeps its own record of when it last tried each one.

run-fill.ps1 runs once at 06:30 for every account on the machine. It reads each application with a link and a blank company, role or location, one subagent per posting, and writes what it found back through /api/applications/autofill with that account's own token.

02 · Page and API

server/ is the API Worker: JSON only, CORS-enabled, and every request is served from a database handle scoped to the person whose token made it. client/ is a separate static-assets Worker serving one HTML file with no build step. It calls the API cross-origin, and the API's URL comes from its gitignored local-config.js. Either half redeploys without the other.

Signing in exchanges a name and password at /api/login for a session token, which the page keeps in localStorage. Accounts are created through /api/users with the ADMIN_TOKEN secret; there is no sign-up page. Edits are row writes, not a shared blob, so a browser edit and a run landing at the same moment don't overwrite each other.

client-react/ is a React rebuild of the page, deployed as its own Worker (job-search-tracker-client-react). It isn't finished and nothing depends on it; client/ is the tracker. See react-adoption-plan.md.

03 · Data boundary

What each search looks for — target companies, the role line, the candidate framing, the geographic scope — is config in D1, keyed by user, and the Worker composes the prompt from it. Resumes and each track's baseline doc are in R2 under the person's user id, read and written through /api/documents.

The machine keeps what it needs to act for each person: tracker.json with their tracker URL and token, and the run logs, under <DataDir>\<user-id>\, gitignored. A run's copy of the documents is cleared when that track next runs.

One table is shared across accounts: company_fetch, the company list every search reads from, with facts about reaching each company's careers site. Which companies are on it is visible across the deployment; who looked at one and when stays with each search (see schema.md). The .claude/skills/job-search-setup/ skill fills in a person's config and documents from a resume and a conversation. The public repo holds only the mechanism.

JobSearchTracker-ArchiveBackupsarchive-backups.ps103:45, as SYSTEMcopies new exports into an archive the everyday account cannot modify

The search and fill tasks are registered by scripts/setup-scheduler.ps1. The two backup tasks are registered by scripts/protect-backups.ps1, a one-time elevated setup, which runs a protected copy of archive-backups.ps1 so SYSTEM never executes a script the everyday account can edit.

API routes

The route table is server/src/routes/index.js: the three routes that run before anyone is signed in, and every route that needs a session. Each handler's comment gives its request and response, and server/README.md's API section has the prose version.
